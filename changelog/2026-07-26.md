## 一、问题背景

### 1.1 当前流程（推理时全量塞入）

```
用户输入 → confirm_intent → retrieve_product_docs → extract_related_modules
  → retrieve_related_data → analyze_test_points_raw（全量原始文档）
  → generate_excel_plan → END
```

`analyze_test_points_raw` 的 human prompt 注入三块数据：

| 变量 | 内容 | 规模 |
|------|------|------|
| `product_docs` | 产品文档全文（ChromaDB 检索） | 10~30 个 chunk，2~8 万 Token |
| `api_definitions` | 接口定义列表（ChromaDB 检索） | 30~80 个接口，1~3 万 Token |
| `related_docs` | 关联模块名（逗号分隔字符串） | 极短 |

单次调用 5~20 万 Token，且每次对话都重新分析同一批文档。

### 1.2 三大死穴

| 问题 | 后果 | 代码表现 |
|------|------|---------|
| **上下文爆炸** | Token 贵、易超限、LLM 丢上下文 | `retrievers.py:359-367` 三块全量文本注入 |
| **噪声干扰** | 文档中的 UI 描述、运营规则淹没接口契约，LLM 编造参数 | 文档写"用户点击按钮"但 API 没有对应字段 |
| **无结构复用** | 同一模块多次对话，每次重新读全文分析 | 对话间 0 缓存 |

## 二、方案：入库预处理 + 推理时结构化调用

### 2.1 两阶段架构

```
┌──────────────────────────────────────────────────────────────────┐
│ 阶段一（前端按钮触发）：场景分析 + 接口映射                         │
│                                                                  │
│ 用户点击"分析测试场景"按钮 ──→ 触发后台任务                        │
│   │                                                              │
│   ├── 该模块下全部产品文档 (product/axure)                         │
│   ├── 该模块下全部接口定义 (api) ← 绑定时已确认关联                 │
│   ├── 关联模块的接口/文档 (BindingOps) ← 跨模块依赖已解析          │
│   │                                                              │
│   ▼                                                              │
│   只做两件事（不生成用例，不分析测试内容）：                         │
│                                                                    │
│   ① 场景分析，提取测试点                                           │
│      例: 设备管理场景 → 添加/删除/修改/查询/导入/导出 6 个功能点   │
│                                                                  │
│   ② 接口分析，场景涉及哪些接口 + 数据流向                           │
│      例: A场景涉及 x, y, z 接口                                    │
│           x 接口产出 order_id → y 接口需要消费                     │
│           z 接口需要从上游获取 user_token                          │
│                                           │                      │
│                                           ▼                      │
│                              存入 SQLite module_analysis 表        │
│                              前端展示场景-接口映射图               │
└──────────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│ 阶段二（推理时）：Phase B 基于场景+接口映射生成用例                 │
│                                                                  │
│ 用户输入 ──→ 检索 module_analysis ──→ Phase B 生成用例             │
│              （场景+接口+数据流）      （不做重复分析）              │
│                                                                  │
│              Token: 每次 2000~5000（下降 10~30 倍）                │
└──────────────────────────────────────────────────────────────────┘
```

**阶段一只做两件事，不越界**：
- ✅ 场景分析：从文档中识别有哪些业务场景，每个场景有哪些功能点（测试点）
- ✅ 接口映射：每个功能点涉及哪些接口，接口间的数据依赖关系
- ❌ 不生成测试用例
- ❌ 不分析测试内容（参数值、断言、预期结果）

### 2.2 分析输出结构：两份独立分析

阶段一只输出两份分析结果，不生成任何测试内容（参数值、断言、预期结果）。

两份分析职责不同、互相补充，Phase B LLM 同时接收两者生成测试用例：

| 分析 | 视角 | 回答的问题 | 产物 |
|------|------|-----------|------|
| **接口维度分析** `api_analysis` | 以单个 API 为中心 | 这个接口需要覆盖哪些测试类型？ | 每个接口的正向/边界/逆向/安全 scope |
| **场景维度分析** `scenario_analysis` | 以业务流程为中心 | 各接口之间有什么依赖和时序约束？ | 跨接口数据流、业务规则链、跨模块约束 |

#### 2.2.1 接口维度分析（`api_analysis`）

以每个 API 为粒度，分析四类覆盖维度：

| 维度 | 说明 | Phase B 展开动作 |
|------|------|-----------------|
| `正向` | 全字段合法值，预期成功 | 生成 1 条正常用例 |
| `边界值` | 字段长度/数值/时间的边界 | 生成边界值用例（最大/最小/临界） |
| `逆向` | 业务规则冲突 + 字段校验错误 | 生成反向用例（预期 [ne] 或 [contains] 错误信息） |
| `安全` | SQL 注入、XSS、越权等 | 生成安全攻击向量用例 |

```json
{
  "module_name": "智慧用电",
  "analyzed_at": "2026-07-28T10:00:00",
  "api_analysis": [
    {
      "api_path": "/electricMeter/add",
      "api_method": "POST",
      "api_name": "新增电表",
      "scope": {
        "正向": ["全字段合法值录入"],
        "边界值": ["编号最大长度", "名称为空字符串", "初始读数最大值"],
        "逆向": ["编号重复", "必填字段缺失", "计费方案编码不存在"],
        "安全": ["编号字段 SQL 注入", "名称字段 XSS"]
      },
      "produces": ["meter_code"],
      "consumes": ["pay_config_code"]
    },
    {
      "api_path": "/electricMeter/delete",
      "api_method": "POST",
      "api_name": "删除电表",
      "scope": {
        "正向": ["删除未绑定的电表"],
        "边界值": [],
        "逆向": ["删除已绑定计费方案的电表", "重复删除同一编码", "删除不存在的编码"],
        "安全": []
      },
      "produces": [],
      "consumes": ["meter_code"]
    },
    {
      "api_path": "/electricMeter/getEle/{code}",
      "api_method": "GET",
      "api_name": "查询电表详情",
      "scope": {
        "正向": ["按编码查询电表完整信息"],
        "边界值": ["编码为空字符串"],
        "逆向": ["查询不存在的编码", "查询已删除的编码"],
        "安全": ["编码路径遍历"]
      },
      "produces": [],
      "consumes": ["meter_code"]
    }
  ]
}
```

**字段说明**：

| 字段 | 说明 |
|------|------|
| `api_analysis[].scope.正向` | 正常业务场景描述列表（Phase B 据此决定 json/params 字段值） |
| `api_analysis[].scope.边界值` | 边界条件描述列表（空数组 = 该接口无边界场景） |
| `api_analysis[].scope.逆向` | 错误处理场景描述列表（包含业务规则冲突和字段校验错误） |
| `api_analysis[].scope.安全` | 安全测试场景描述列表（空数组 = 无安全风险点） |
| `api_analysis[].produces` | 该接口产出的变量（供下游接口消费） |
| `api_analysis[].consumes` | 该接口需要从上游获取的变量 |

#### 2.2.2 场景维度分析（`scenario_analysis`）

以业务流程为粒度，描述接口间的依赖关系、时序约束和跨模块影响。LLM 据此编排多步骤测试用例的调用顺序和数据传递。

```json
{
  "scenario_analysis": [
    {
      "scenario_id": "S001",
      "scenario_name": "企业入住 → 绑定电表 → 退租解绑",
      "description": "企业入驻园区后绑定电表，签约计费方案，退租时需先解约再删除",
      "steps": [
        {
          "order": 1,
          "api": "POST /tenant/add",
          "role": "创建企业租户，产出 tenant_code",
          "data_depends_on": []
        },
        {
          "order": 2,
          "api": "POST /payConfig/bindMeters",
          "role": "为租户绑定电表并签约计费方案，消费 tenant_code + meter_code",
          "data_depends_on": ["tenant_code", "meter_code"]
        },
        {
          "order": 3,
          "api": "POST /payConfig/delete",
          "role": "退租时删除计费方案——若电表仍绑定则失败",
          "data_depends_on": ["pay_config_code"],
          "failure_condition": "电表未解绑时删除计费方案 → 预期 '该方案已绑定资源，无法删除'"
        },
        {
          "order": 4,
          "api": "POST /meterDevice/delete",
          "role": "解绑后删除电表",
          "data_depends_on": ["meter_code"]
        }
      ],
      "cross_module_deps": [
        {
          "module": "计费规则",
          "constraint": "电表绑定计费方案后不可删除，删除前必须解绑",
          "affected_api": "POST /meterDevice/delete"
        }
      ]
    },
    {
      "scenario_id": "S002",
      "scenario_name": "企业签约 → 账单生成 → 财务确认",
      "description": "企业签订计费合约后系统自动生成账单，需到财务模块确认合约是否已生成对应账单",
      "steps": [
        {
          "order": 1,
          "api": "POST /payConfig/add",
          "role": "为企业创建计费合约，产出 contract_code",
          "data_depends_on": ["tenant_code"]
        },
        {
          "order": 2,
          "api": "GET /finance/bill/query",
          "role": "到财务模块查询合约是否已生成账单，消费 contract_code",
          "data_depends_on": ["contract_code"],
          "cross_module": "财务模块"
        },
        {
          "order": 3,
          "api": "POST /finance/bill/confirm",
          "role": "确认账单金额与合约一致",
          "data_depends_on": ["bill_id"],
          "cross_module": "财务模块"
        }
      ],
      "cross_module_deps": [
        {
          "module": "财务管理",
          "constraint": "计费合约创建后财务模块自动生成账单，测试需跨模块验证",
          "affected_api": "GET /finance/bill/query"
        }
      ]
    }
  ]
}
```

**字段说明**：

| 字段 | 层级 | 说明 |
|------|------|------|
| `scenario_analysis[].scenario_name` | 场景 | 业务流程名称 |
| `scenario_analysis[].description` | 场景 | 场景一句话概述 |
| `steps[].order` | 步骤 | 执行顺序（1-based） |
| `steps[].role` | 步骤 | 该步骤在流程中的角色/目的 |
| `steps[].data_depends_on` | 步骤 | 该步骤消费的数据（来自前序步骤的 produces） |
| `steps[].failure_condition` | 步骤（可选） | 该步骤在什么条件下预期失败 |
| `steps[].cross_module` | 步骤（可选） | 该步骤是否跨模块（需到其他模块验证） |
| `cross_module_deps[].constraint` | 跨模块约束 | 跨模块的业务规则 |
| `cross_module_deps[].affected_api` | 跨模块约束 | 受约束影响的接口 |

#### 2.2.3 两份分析如何协作

```
┌──────────────────────────────────────────────────────────────────┐
│ Phase B LLM 输入                                                  │
│                                                                  │
│  ┌─────────────────────┐    ┌─────────────────────────────┐      │
│  │ api_analysis        │    │ scenario_analysis           │      │
│  │                     │    │                             │      │
│  │ · 每个接口的 scope  │    │ · 业务流程 + 步骤顺序       │      │
│  │ · produces/consumes │    │ · 数据依赖链                │      │
│  │                     │    │ · 跨模块约束                │      │
│  └────────┬────────────┘    └────────────┬────────────────┘      │
│           │                              │                        │
│           └──────────┬───────────────────┘                        │
│                      ▼                                            │
│  LLM 生成测试用例:                                                │
│    ① 按 api_analysis.scope 逐条展开 → 每个维度生成对应用例         │
│    ② 按 scenario_analysis.steps 编排 → 正向用例用指定顺序 +      │
│       数据依赖链串联                                               │
│    ③ 按 scenario_analysis.cross_module_deps → 生成跨模块验证步骤  │
│    ④ 正向用例优先编排（scenario 步骤顺序），反向/安全用例独立      │
│       插入（不依赖 scenario 流程）                                  │
│                                                                  │
│  例: api_analysis 说 /meterDevice/delete 有 "删除已绑定电表"      │
│      反向场景 → LLM 直接生成 1 条反向用例，无需 scenario 上下文    │
│                                                                  │
│      scenario_analysis 说 "退租需先解约再删除" → LLM 编排         │
│      多步骤正向用例: 创建企业 → 绑定电表 → 删除(预期失败) →       │
│      解绑 → 删除(预期成功)                                        │
└──────────────────────────────────────────────────────────────────┘
```

**职责边界**：

| 问题 | 由哪个分析回答 |
|------|--------------|
| "新增电表需要测哪些错误情况？" | `api_analysis` — scope.逆向 |
| "删除企业之前要做什么前置操作？" | `scenario_analysis` — steps + data_depends_on |
| "这个接口有没有 SQL 注入风险？" | `api_analysis` — scope.安全 |
| "签约后账单在哪个模块验证？" | `scenario_analysis` — cross_module_deps |
| "这个接口需要的参数从哪来？" | `api_analysis` — consumes → 查 produces 匹配 |

#### 2.2.4 scope 标签规范

| 类别 | 标签 | Phase B 展开动作 |
|------|------|-----------------|
| 正向 | `正向` | 按 scenario 步骤顺序生成正常用例 |
| 边界值 | `边界值` | 生成边界值用例，LLM 取标签中指定的具体边界 |
| 逆向 | `逆向` | 生成业务规则冲突 + 字段校验错误用例（含 SQL 注入/XSS 等可预期错误响应），预期 `[ne]` 或 `[contains]` 错误提示 |
| 安全 | `安全` | 生成安全攻击向量用例（越权、未授权访问、路径遍历等攻击向量，**不属于逆向**） |

> ⚠️ `安全` 与 `逆向` 不重叠。逆向 = 可预期错误响应（服务器返回错误码+信息），安全 = 攻击向量（未授权行为）。SQL 注入/XSS 属于逆向（预期服务器拒绝并返回错误），不属于安全。

### 2.3 数据库存储格式

分析结果存入 SQLite，允许用户手动修改后再交给 Phase B。

**表结构**：

```sql
CREATE TABLE module_analysis (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    module_id     TEXT NOT NULL UNIQUE,          -- modules.id (UUID)，外键关联，级联删除
    module_name   TEXT NOT NULL,                 -- 冗余字段，用于前端展示
    analysis_json TEXT NOT NULL,                 -- 完整 JSON（§2.2 结构）
    status        TEXT DEFAULT 'draft',          -- draft | reviewed | approved（仅前端追踪，不用于 Phase B 门控）
    extracted_at  TEXT,                          -- LLM 提取时间
    modified_at   TEXT,                          -- 最后手动修改时间
    modified_by   TEXT,                          -- 修改人（前端用户标识）
    version       INTEGER DEFAULT 1,             -- 修改计数器（单用户场景，暂不作乐观锁）
    FOREIGN KEY (module_id) REFERENCES modules(id) ON DELETE CASCADE
);
```

> **主键选型**：用 `module_id`（UUID）而非 `module_name`。模块可被 `ModuleOps.rename_module` 重命名，`module_id` 不变且与 `modules` 表主键一致。

**状态流转**（`status` 仅用于前端用户追踪）：

```
draft ──→ reviewed ──→ approved
  │                      │
  └── 用户编辑后保存 ────┘
  │
  └── 用户点击"重新分析" → LLM 重新生成，覆盖旧 JSON，status 重置为 draft
```

**前端编辑接口**：

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/module/{name}/analyze-scenarios` | POST | 触发 LLM 分析（status=draft） |
| `/api/module/{name}/analysis` | GET | 读取当前 analysis JSON |
| `/api/module/{name}/analysis` | PUT | 手动修改保存（status=reviewed，version++） |
| `/api/module/{name}/analysis/approve` | POST | 标记为 approved |

**Phase B 消费逻辑（简化）**：**有 analysis 就用，没有才降级到全量原文**。不检查 `status`——即使用户编辑后忘了 approve（status=reviewed），Phase B 仍使用已有 analysis，不静默降级。

**为什么需要手动修改**：
- LLM 可能漏掉某个功能点的 scope（如忘了"删除电表"的边界场景）
- 用户比 LLM 更了解业务——用户知道"这个模块的导入功能不需要测性能"
- scope 标签可以增删改：用户加一条 `"边界-尖峰时段临界值"`，Phase B 就会多生成一条用例

### 2.3 Phase B 输入变化

Phase B 的 `analyze_test_points_raw` 保持现有逻辑（仍需做测试场景分析），但新增 `module_analysis` 作为优先输入。当 analysis 存在时，LLM 跳过场景识别，直接基于已知的场景+接口映射生成用例。

```python
human_parts = ["### 用户需求\n{user_context}"]

if module_analysis:
    # 优先路径：已有场景+接口映射
    human_parts.append(
        "### 模块场景与接口分析（权威数据源）\n"
        "{module_analysis}\n\n"
        "上述分析已列出所有场景、功能点、涉及接口及数据流向。"
        "请基于此分析生成测试用例，不要重复分析场景。"
    )
else:
    # 降级路径：全量原文（当前逻辑）
    human_parts.append("### 产品文档\n{product_docs}")
    human_parts.append("### 关联模块\n{related_docs}")

human_parts.append("### 接口定义\n{api_definitions}")
human_parts.append("请分析以上信息并生成测试用例。")
```

| 变量 | 改前 | 改后（有analysis） |
|------|------|------|
| `product_docs` | 全量原文 2~8 万 Token | **跳过**，analysis 已包含场景摘要 |
| `module_analysis` | — | **新增**：场景+接口映射 JSON，500~2000 Token |
| `api_definitions` | 全量列表 | 保留（接口参数详情不在 analysis 中） |

Phase B LLM 不再需要"识别有哪些场景、每个场景涉及哪些接口"——这些已经在前端按钮触发的分析中完成了。

### 2.4 Token 节省估算

| 场景 | 改前 Token/次 | 改后 Token/次 | 节省 |
|------|:---:|:---:|:---:|
| 单模块（8 个子模块，30 API） | ~120,000 | ~5,000 | 96% |
| 单模块（3 个子模块，10 API） | ~50,000 | ~3,000 | 94% |
| 月调用 50 次 | ~4,250,000 | ~200,000 | 95% |

## 三、实施步骤

   ```python
   class AnalysisOps:
       @staticmethod
       def get_by_module_id(session, module_id: str) -> ModuleAnalysis | None:
           """按 module_id 查询分析记录。"""
           return session.query(ModuleAnalysis).filter_by(module_id=module_id).first()

       @staticmethod
       def upsert(session, module_id: str, module_name: str,
                  analysis_json: str) -> ModuleAnalysis:
           """创建或覆盖分析记录（同一 module_id 只有一条）。"""

       @staticmethod

           """删除模块的分析记录（绑定变更时调用）。"""
   ```

6. **绑定变更触发失效**：任何模块绑定关系变更前，若该模块已有 `module_analysis` 记录，前端弹窗确认后才执行。

   **触发范围**（4 类操作）：
   | 操作 | 前端函数 | 后端端点 |
   |------|---------|---------|
   | 绑定文档到模块 | `bindDocToModule(docId, docType)` | `POST /api/bindings` |
   | 解绑文档 | `unbindDocFromModule(docId, docType)` | `DELETE /api/bindings` |
   | 关联模块 | `linkModuleToModule()` | `POST /api/bindings` |
   | 解除模块关联 | `unlinkModuleFromModule(targetName)` | `DELETE /api/bindings` |

   **交互流程**：
   ```
   用户点击"绑定/解绑/关联/解除关联"
     │
     ├── 前端调用 GET /api/module/{name}/analysis
     │     │
     │     ├── 返回 null（无 analysis） → 直接执行操作（无需弹窗）
     │     │
     │     └── 返回 analysis JSON（已有分析）
     │           │
     │           ▼
     │         弹窗："修改绑定关系后，已有的场景分析将失效，需要重新生成。确认修改？"
     │           │
     │           ├── [取消] → 不执行任何操作，关闭弹窗
     │           │
     │           └── [确认] → 执行两步（同一事务或顺序执行）：
     │                         1. 执行原绑定操作（POST/DELETE /api/bindings）
     │                         2. DELETE /api/module/{name}/analysis
     │                            （删除旧 module_analysis，级联清空相关缓存）
     │                         3. 前端 toast："已更新绑定，请重新生成场景分析"
     │                         4. 刷新绑定列表 + 隐藏"分析测试场景"按钮
     ```

   **前后端分工**：
   - **前端**：在 4 个操作函数开头插入 `checkAnalysisAndConfirm()` 调用，返回 `true` 才继续执行
   - **后端**：不拦截（不做两阶段提交），由前端控制流程。删除 analysis 和绑定操作各自独立请求

   **为什么是弹窗而不是静默删除**：
   - 用户可能不知道"改绑定会导致分析过期"——弹窗让因果关系显式可见
   - 如果静默删除，用户点击 Phase B 时才发现 analysis 不见了，排查成本高
   - 弹窗提供了"取消"选项——用户可能在错误模块上操作，给他反悔的机会

## 五、决策记录

| # | 决策点 | 结论 | 理由 |
|---|--------|------|------|
| 1 | 分析结果存放 | SQLite `module_analysis` 表，`module_id` (UUID) 作唯一键 | 模块可重命名，UUID 稳定；外键关联 `modules.id`，级联删除 |
| 2 | 分析触发时机 | **前端按钮手动触发**（绑定完成后用户点击"分析测试场景"） | 绑定完成 ≠ 用户准备好了，手动触发给用户控制权 |
| 3 | 分析范围 | **只做场景+接口映射**，不生成用例，不分析测试内容（参数值/断言/预期结果） | 职责边界清晰：阶段一管"测什么"，Phase B 管"怎么测" |
| 4 | 降级策略 | **有 analysis 就用，没有才降级**（不检查 status） | 避免用户编辑后忘了 approve 导致静默降级；status 仅前端追踪用 |
| 5 | Phase B 变化 | 保留 `analyze_test_points_raw`，新增 `{module_analysis}` 可选入参 | 有 analysis 时跳过场景识别，没有时走原逻辑 |
| 6 | 关联模块 | analysis 利用 BindingOps 跨模块关系，产出 `cross_module_refs` | 关联模块从保护对象变成分析数据源 |
| 7 | 前端可视化 | 分析完成后展示场景-接口映射图（场景卡片+API标签+数据流向箭头） | 用户进入 Phase B 之前就能看到完整的场景和接口关系 |
| 8 | 表名 | `ModuleAnalysis`（不是 `ModuleMetadata`） | 准确反映内容：场景+接口分析，不是元数据 |
| 9 | `test_point.scope` | 每个测试点带 `scope` 数组（正向/边界-具体值/逆向-具体场景/安全） | Phase B 不猜覆盖类型，直接按 scope 逐条展开，杜绝漏测 |
| 10 | 数据库 status | `draft→reviewed→approved` 仅用于前端追踪，**不作为 Phase B 门控条件** | 简化逻辑：有分析就用，不关注审批状态 |
| 11 | 手动修改 | 提供 GET/PUT API，前端编辑 scope / test_points / data_flow | LLM 可能漏 scope，用户比 LLM 更了解业务 |
| 12 | 文档检索方式 | Phase A 用 ChromaDB `get_doc_chunks(doc_id)` 精确 metadata 查询，**不用向量相似度检索** | 绑定关系已精确确定文档范围，向量检索的 top-k 截断反而丢失 chunk |
| 13 | 绑定变更处理 | 弹窗确认 → 执行绑定操作 + 删除旧 `module_analysis` | 保证 analysis 与当前绑定关系一致，避免过期数据 |
| 14 | 安全标签 | `安全` 独立于 `逆向`；删除 `反向-SQL注入`/`反向-XSS` 标签 | 逆向 = 可预期错误响应（含 SQL 注入/XSS），安全 = 攻击向量（越权/路径遍历） |
| 15 | 路径参数替换 | **代码层** `${get_extract_data(xxx)}` 替换，不依赖框架改造 | 零外部依赖，立即可用；框架原生支持列为后续优化项 |
| 16 | `_annotations` 注入点 | `_generate_one_yaml` 中 LLM JSON parse 后 → Pydantic 构造前 | 代码注入，不依赖 LLM 行为；`_invoke_structured` 新增 `pre_validate` 回调 |

## 六、接口特殊标识方案 ①：导出/导入类接口（`is_export`）

> 来源：`chongelog/2026-07-27_yaml_check_SmartElectricity_21_fix_plan.md` 修复 2
> 状态：方案已记录，待实施

### 6.1 问题

导出/下载/导入模板类接口返回二进制流（Excel/文件），`res.json()` 降级为 `{}`，`eq: {$.retCode: 0}` 断言必然失败。LLM 默认对所有接口输出相同断言模式，不知道哪些接口需要特殊处理。

本次智慧用电_24 命中：`/electricBillApartment/export`、`/electricBillEnterprise/exportBillEnterprise`、`/shareBill/template/enterprise`。

### 6.2 方案：接口入库阶段标注 → 校验阶段按标识放行

```
Phase B/C 边界 (nodes.py _generate_excel_plan_node)
  └─ 落盘 api_defs.json 时，分析每个接口 URL/name
     └─ 命中 export/import/template/download/upload → 标注 is_export: true
     
Phase C YAML 校验 (response_model.py)
  └─ StepData 校验器检测到 is_export=true 的接口
     └─ 跳过"断言为空"的拦截，允许不写 validation
```

### 6.3 实施步骤（通过 §8 ApiAnnotationRegistry 统一注册表实现）

**第一步：接口定义阶段标注类型**

文件：`agent_components/nodes.py`（约 116-117 行，`all_apis_dict` 构建处）

在落盘 `api_defs.json` 前，调用 `ApiAnnotationRegistry.apply_all(api)`，由已注册的 `is_export` 检测器自动匹配并写入 `annotations.is_export`：

```python
# nodes.py all_apis_dict 构建后新增（一行替代硬编码关键词遍历）
from agent_components.api_annotations import ApiAnnotationRegistry

for api in all_apis_dict:
    ApiAnnotationRegistry.apply_all(api)
```

检测器逻辑定义见 §8.6（按 URL/name 匹配 `export/import/template/download/upload` 关键词）。写入 `api_defs.json` 后的格式：

```json
{
  "url": "/electricBillApartment/export",
  "method": "post",
  "annotations": {
    "is_export": { "active": true, "source": "auto" }
  }
}
```

**第二步：校验阶段识别标识放行**

文件：`prompts/response_model.py`（`StepData.validate_validation_not_empty` 校验器）

校验器通过 `_annotations` 读取标注（`_annotations` 由 §8.5 注入点从 `api_defs.json` 的 `annotations` 字段复制到 `baseInfo`）：

```python
# StepData.validate_validation_not_empty（改造后）
@model_validator(mode="after")
def validate_validation_not_empty(self) -> "StepData":
    annotations = self.baseInfo.get("_annotations", None)
    for tc in self.testCase:
        if not tc.validation:
            if ApiAnnotationRegistry.is_active(annotations, "is_export"):
                # 导出接口 → 允许空断言，由代码强制写入 contains: {status_code: 200}
                continue
            raise ValueError("testCase 缺少 validation 字段")
    return self
```

文件：`agent_components/generators/__init__.py`（`_generate_one_yaml` 写盘前）

## 七、接口特殊标识方案 ②：RESTful 路径参数接口（`has_path_params`）

> 来源：智慧用电_24 终态失败分析（2026-07-28）
> 状态：方案已记录，待实施

### 7.1 问题

RESTful 风格接口的 URL 包含路径参数模板（如 `/electricMeter/needToUploadInTime/{code}`、`/payConfig/delete/{code}`）。当前 `StepData` 校验器形成了**逻辑死锁**：

| 校验规则 | 拦截内容 | 位置 |
|---------|---------|------|
| `url含动态占位符` | url 中出现 `${get_extract_data(...)}` | `response_model.py:575-584` |
| `url含字面量路径参数` | url 中出现 `{xxx}` 字面量模板 | `response_model.py:564-574` |

LLM 在两个错误模式之间来回切换——写入 `${...}` 被第一条拦截，写入 `{code}` 被第二条拦截——**不存在合法的写法**。

本次智慧用电_24 命中实例：
- `GEN-FAIL-R2-012`：`/electricMeter/needToUploadInTime/{code}` — R1 写 `${get_extract_data(...)}` 被拦截，R2 写 `{code}` 被拦截
- `GEN-FAIL-R2-011`：`/payConfig/delete/` — R1 写 `params` 被拦截，R2 写 `${...}` 被拦截

### 7.2 方案：接口入库阶段检测路径参数 → 校验阶段按标识放行

```
Phase B/C 边界 (nodes.py _generate_excel_plan_node)
  └─ 落盘 api_defs.json 时，ApiAnnotationRegistry.apply_all(api)
     └─ has_path_params 检测器命中 URL 含 {xxx} 模式
        → 写入 annotations.has_path_params: {active: true, source: "auto", path_params: ["code", ...]}
     
Phase C YAML 校验 (response_model.py StepData.validate_url_no_placeholder)
  └─ 检测到 url 含 {xxx} 时
     └─ 查 baseInfo._annotations.has_path_params.active → true → 放行
```

### 7.3 实施步骤（通过 §8 ApiAnnotationRegistry 统一注册表实现）

```python
# StepData.validate_url_no_placeholder（改造后）
@model_validator(mode="after")
def validate_url_no_placeholder(self) -> "StepData":
    url = str(self.baseInfo.get("url", ""))
    annotations = self.baseInfo.get("_annotations", None)

    # {xxx} 字面量路径参数检测
    _literal = re.search(r'\{(\w+)\}', url)
    if _literal:
        if not ApiAnnotationRegistry.is_active(annotations, "has_path_params"):
            # 未标注 → 按原逻辑拦截
            raise ValueError(f"url 字段含路径参数模板 '{{{_literal.group(1)}}}'...")
        # 已标注 → 静默放行

    # ${} 动态占位符检测（不受 has_path_params 影响，独立判断）
    if "${" in url:
        raise ValueError("url 字段禁止使用 ${} 动态占位符...")
    return self
```

## 八、统一架构：`ApiAnnotationRegistry` — API 异常标识注册表

> 设计日期：2026-07-28
> 状态：方案设计阶段
> 吸收：§六（`is_export`）、§七（`has_path_params`）及未来扩展的所有接口级特殊处理标识

### 8.1 设计动机

§六和 §七暴露了一个共同模式：需要在接口入库阶段对 API 做特殊标注，校验阶段按标注调整行为。如果继续用零散的 `is_xxx: true` 布尔字段硬编码，每增加一个异常类型就要改 3~4 个文件，且前端无法统一展示。

**目标**：一个可注册、可检测、可人工干预的异常标识管理系统，覆盖三个角色：

| 角色 | 需求 |
|------|------|
| **入库阶段** (nodes.py) | 自动检测 + 写入 `api_defs.json` |
| **校验阶段** (response_model.py) | 按标识判定是否跳过拦截或调整行为 |
| **前端确认页** | 展示已标注类型、允许人工增删改、标识来源可追溯 |

### 8.2 核心数据结构

#### 8.2.1 `annotations` 字段（api_defs.json 内每个接口 dict）

```json
{
  "name": "通知电表上报",
  "url": "/electricMeter/needToUploadInTime/{code}",
  "method": "get",
  "annotations": {
    "has_path_params": {
      "active": true,
      "source": "auto",
      "path_params": ["code"]
    },
    "is_export": {
      "active": false,
      "source": "manual"
    }
  }
}
```

**字段约定**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `annotations` | `dict[str, dict] \| null` | **门控字段**。`null` / 不存在 → 接口无任何异常标识，入库时全量自动检测。非空 → 已有人工干预，自动检测只补充缺失 key，不覆盖已有。 |
| `annotations.<key>.active` | `bool` | 是否激活。用户可关闭自动检测的标识而不用删除整条记录 |
| `annotations.<key>.source` | `"auto" \| "manual"` | 来源。`auto` = 入库检测器自动添加；`manual` = 用户在前端手动添加或修改 |
| `annotations.<key>.<meta>` | `any` | 各类型自定义的附加元数据（如 `path_params: ["code"]`） |

#### 8.2.2 `ApiAnnotationDef` — 单个异常标识类型定义

```python
# 文件: agent_components/api_annotations.py

from dataclasses import dataclass
from typing import Any, Callable

@dataclass
class ApiAnnotationDef:
    """单个 API 异常标识的元数据定义"""
    key: str                              # 唯一标识: "is_export" / "has_path_params"
    label: str                            # 前端展示名: "导出/导入类接口"
    description: str                      # 悬停提示文本
    category: str                         # 分组: "request" | "response" | "lifecycle"
    detector: Callable[[dict], tuple[bool, dict | None]]
    # 自动检测函数: (api_dict) -> (匹配与否, 附加元数据或 None)
```

#### 8.2.3 `ApiAnnotationRegistry` — 注册表（类方法集合）

```python
class ApiAnnotationRegistry:
    """API 异常标识注册表 — 统一入口"""
    
    _registry: dict[str, ApiAnnotationDef] = {}
    
    # ========== 注册管理 ==========
    
    @classmethod
    def register(cls, defn: ApiAnnotationDef) -> None:
        """注册一个新的异常类型"""
    
    @classmethod
    def get_type(cls, key: str) -> ApiAnnotationDef | None:
        """按 key 查询单个类型定义"""
    
    @classmethod
    def get_types(cls) -> list[ApiAnnotationDef]:
        """返回全部已注册类型列表 → 供前端渲染选项"""
    
    # ========== 检测逻辑 ==========
    
    @classmethod
    def detect_all(cls, api_dict: dict) -> dict[str, dict]:
        """对单个 api_dict 跑全部检测器，返回 {key: {active, source, ...meta}}"""
    
    @classmethod
    def apply_all(cls, api_dict: dict) -> dict:
        """检测 + 写入 annotations 字段（级联规则见 §8.3），返回修改后的 dict"""
    
    # ========== 校验辅助 ==========
    
    @classmethod
    def is_active(cls, annotations: dict | None, key: str) -> bool:
        """供 validator 调用：该标识是否激活"""
    
    @classmethod
    def has_any(cls, annotations: dict | None) -> bool:
        """是否有任意激活的异常标识"""
```

### 8.3 两级规则：检测（始终全量）+ 校验放行（精准逐条）

整个系统分两层，职责分离：

```
┌─────────────────────────────────────────────────────────────────┐
│ 第一层：检测（ingest 阶段，nodes.py）                             │
│                                                                  │
│ 对每个 API 跑全部已注册检测器，无论 annotations 是否已存在。       │
│ annotations 非空不会"关闭"检测——检测永远全量。                    │
│                                                                  │
│ apply_all(api_dict):                                             │
│   for each registered type:                                      │
│     matched, meta = type.detector(api_dict)                      │
│     if matched 且 annotations 中该 key 不存在:                    │
│       annotations[key] = {active: true, source: "auto", ...meta} │
│     if matched 但 annotations 中已有（人工改过）:                 │
│       保留人工版本（source: "manual" 的 active/source 不被覆盖）  │
│     if not matched:                                              │
│       该 key 不出现（除非用户手动添加过）                          │
│                                                                  │
│ → 结果: api_dict["annotations"] 同时包含 auto + manual 键         │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ 第二层：校验放行（Phase C 阶段，response_model.py）               │
│                                                                  │
│ 每个 validator 在抛出拦截前查：该 API 是否有对应的激活标识。       │
│ 放行是精准的、逐条的——一个标识只放行一条校验规则。                 │
│                                                                  │
│ 规则:                                                            │
│   - annotations 为空（没有任何激活标识）                           │
│     → 所有校验规则全量执行，无任何放行                              │
│                                                                  │
│   - annotations 含 is_export 且 active=true                       │
│     → 只跳过"断言为空"这一条校验                                   │
│     → 其他所有校验（url占位符、method/body匹配、extract前缀等）    │
│       照常执行，不受任何影响                                       │
│                                                                  │
│   - annotations 含 has_path_params 且 active=true                 │
│     → 只跳过"url 含 {xxx} 字面量路径参数"这一条校验                 │
│     → 其他所有校验（${}动态占位符、断言、method/body匹配等）        │
│       照常执行，不受任何影响                                       │
│                                                                  │
│   - annotations 同时含 is_export + has_path_params                │
│     → 跳过"断言为空" + "url 含 {xxx} 字面量" 两条校验              │
│     → 其他所有校验照常执行，互不干扰                                │
└─────────────────────────────────────────────────────────────────┘
```

**一句话总结**：annotations 里的每个标识是一把"精准手术刀"——只切掉它对应的那条校验拦截，其他一切照旧。标识之间互不干扰，也不存在"有了标识就放松全部检查"的情况。

### 8.5 校验阶段集成

**多标识并存行为**：当 `annotations` 同时含 `has_path_params` + `is_export` 时：

```
接口: GET /shareBill/template/enterprise/{code}
annotations: { has_path_params: {active:true}, is_export: {active:true} }

校验结果:
  ✅ url含字面量路径参数  → 跳过（has_path_params 放行 {code}）
  ✅ 断言为空             → 跳过（is_export 放行）
  ❌ url含动态占位符      → 照样检查（${...} 仍被拦截，两个标识都不放行此项）
  ❌ GET/DELETE误用json  → 照样检查（两个标识都不放行此项）
  ❌ extract缺$前缀       → 照样检查（两个标识都不放行此项）
  ❌ POST误用params       → 照样检查（两个标识都不放行此项）
```

> **核心约束**：每个 annotation key 只豁免一条校验规则。两个 key 互不干扰，也不会因为"有标识"就放水。没被任何 key 覆盖的规则照常全量执行。

**注入机制**：`_annotations` 由代码在 `_generate_one_yaml` 中注入，不依赖 LLM 行为。精准注入点在 LLM JSON 输出 → Pydantic `TestData` 构造之间：

```
_generate_one_yaml(row, api_defs_json, ...)
  │
  ├── 阶段 1: LLM thinking → 自由文本分析
  ├── 阶段 2: LLM json_mode → JSON 字符串
  │     ↓
  │   json.loads() → parsed dict
  │     ↓
  │   ┌─────────────────────────────────────────────┐
  │   │ ★ 代码注入 _annotations（不依赖 LLM）         │
  │   │                                              │
  │   │ for step in parsed["data"]:                  │
  │   │     url = step["baseInfo"]["url"]             │
  │   │     api = lookup_api_by_url(url, api_defs)    │
  │   │     if api and api.get("annotations"):        │
  │   │         step["baseInfo"]["_annotations"]       │
  │   │             = api["annotations"]               │
  │   └─────────────────────────────────────────────┘
  │     ↓
  │   TestData(**parsed)  ← Pydantic 校验器运行，此时 _annotations 已可用
  │
  └── 路径参数替换（§7.3）→ yaml.dump() → 写盘
```

**实现方式**：`_invoke_structured` 新增 `pre_validate` 回调参数。调用侧传入一个闭包，在 JSON parse 后、Pydantic 构造前执行注入。

**安全验证**：`validate_no_params_in_baseinfo` 只检查 `params`/`json`/`data` 三个 key，`_annotations` 不会被拦截。

#### 步骤 3.1：`response_model.py` — validators 增加 `is_active` 判断

| 项 | 内容 |

#### 步骤 3.2：`generators/__init__.py` — `_annotations` 注入 + `pre_validate` 回调

| 项 | 内容 |
|:---|:---|
| **文件** | `agent_components/generators/__init__.py` |
| **位置** | `_invoke_structured` 方法（新增 `pre_validate` 参数）+ `_generate_one_yaml` 调用处 |
| **内容** | `_invoke_structured` 在 `json.loads()` 后、Pydantic 构造前执行 `pre_validate(parsed_dict)` |
| **参考** | §8.5 "注入机制" |

**实施要点**：
- `_invoke_structured` 新增参数 `pre_validate: Callable[[dict], None] | None = None`，在 `chain.invoke()` 返回 JSON 字符串后：
  ```python
  parsed = json.loads(raw_json)  # 现有逻辑
  if pre_validate:
      pre_validate(parsed)        # 新增：注入 _annotations
  result = model_class(**parsed)  # 现有逻辑：Pydantic 校验
  ```
- `_generate_one_yaml` 调用时传入闭包：
  ```python
  api_defs_list = json.loads(api_defs_json)
  
  def inject_annotations(parsed):
      for step in parsed.get("data", []):
          url = step.get("baseInfo", {}).get("url", "")
          api = _lookup_api_by_url(url, api_defs_list)
          if api and api.get("annotations"):
              step["baseInfo"]["_annotations"] = api["annotations"]
  
  result = self._invoke_structured(
      ..., pre_validate=inject_annotations, ...
  )
  ```

**注意点**：
- `_lookup_api_by_url(url, api_defs_list)` 需要做 URL 匹配：生成的 URL 可能带 `{code}` 等占位符，`api_defs` 中也有 `{code}`，需要先规范化再比较（去掉 `${...}` 动态部分，保留 `{xxx}` 模板部分）
- 找不到匹配时静默跳过（不注入 `_annotations`）——这意味着校验器看到 `None`，走全量校验
- `pre_validate` 抛异常时不要吞掉，让它传播到外层的 `_invoke_structured` 重试机制

#### 步骤 3.3：`generators/__init__.py` — 路径参数替换 + 导出断言强制写入

| 项 | 内容 |
|:---|:---|
| **文件** | `agent_components/generators/__init__.py` |
| **位置** | `_generate_one_yaml`，Pydantic 校验通过后、`yaml.dump()` 写盘前 |
| **内容** | 两段代码逻辑：① `has_path_params` → `{xxx}` 替换为 `${get_extract_data(xxx)}` ② `is_export` → 强制写入 `contains: {status_code: 200}` |
| **参考** | §6.3 第三步、§7.3 第三步 |

**实施要点**：
```python
# Pydantic 校验通过后、yaml.dump() 前

# ① 路径参数替换
for step in result.data:
    annotations = step.baseInfo.get("_annotations", {})
    hp = annotations.get("has_path_params", {})
    if hp.get("active"):
        url = str(step.baseInfo.get("url", ""))
        for param in hp.get("path_params", []):
            url = url.replace(f"{{{param}}}",
                              f"${{get_extract_data({param})}}")
        step.baseInfo["url"] = url

# ② 导出接口断言强制写入
for step in result.data:
    annotations = step.baseInfo.get("_annotations", {})
    if annotations.get("is_export", {}).get("active"):
        for tc in step.testCase:
            tc.validation = [{"contains": {"status_code": 200}}]
```

**注意点**：
- 顺序：① 路径参数替换 必须在 ② 断言写入之前——两者独立，不互依赖，但都必须在 `yaml.dump()` 之前
- 路径参数替换后 URL 含 `${get_extract_data(...)}`，写入 YAML 后框架 `apiutil.py` 的 `replace_load()` 会在运行时解析——框架已支持此格式（YAML_SPECIFICATION v2.1）
- `result.data` 是 Pydantic `StepData` 对象列表，`step.baseInfo` 是 dict，直接修改不影响 Pydantic 模型（模型已构造完毕）
- 替换前确认 `path_params` 列表来自 `annotations` 元数据，不是正则重新从 URL 提取——避免二次替换

```python
def _analyze_test_points_raw(self, state: State):
    from database import get_session_ctx

    confirmed_module = state.get("confirmed_module", "")
    analysis_json = None
    with get_session_ctx() as session:
        mod = ModuleOps.get_by_name(session, confirmed_module)
        if mod:
            record = AnalysisOps.get_by_module_id(session, mod.id)
            if record:
                analysis_json = record.analysis_json

    # ... 构建 docs_text / apis_text ...
    
    if analysis_json:
        prompt_vars["module_analysis"] = analysis_json
        # 跳过 product_docs 检索
```

### Phase 6：绑定变更保护

#### 步骤 6.1：前端弹窗确认 + 删除 analysis

| 项 | 内容 |
|:---|:---|
| **文件** | 前端（4 个绑定操作函数）+ `web/routes/modules.py` |
| **内容** | 绑定/解绑/关联/解除关联前，若模块已有 analysis，弹窗确认后执行操作 + 删除旧 analysis |
| **参考** | §4.1（绑定变更触发失效） |

**实施要点**：
- 前端在 4 个操作函数（`bindDocToModule`、`unbindDocFromModule`、`linkModuleToModule`、`unlinkModuleFromModule`）开头插入 `checkAnalysisAndConfirm()`
- `checkAnalysisAndConfirm()` 逻辑：
  1. `GET /api/module/{name}/analysis`
  2. 返回 `null` → 返回 `true`（直接通过）
  3. 返回 JSON → 弹窗，用户确认 → 返回 `true`，取消 → 返回 `false`
- 用户确认后：先执行绑定操作，成功后 `DELETE /api/module/{name}/analysis`

**注意点**：
- 绑定操作和删除 analysis 是两个独立请求，不需要事务——即使删除失败，analysis 仍可用（只是可能过期），不会阻塞绑定操作
- 4 个操作无误伤——只有当前模块的 analysis 被删除，不影响其他模块
- 关联模块被删除时，引用该模块的其他模块的 analysis 不做级联删除——由用户自行决定何时重新分析
