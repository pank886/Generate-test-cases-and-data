## 〇、背景：三个待解问题

- **问题1** 权威数据源不权威 → 接口文档可能与实际行为不符，需要验证探测
- **问题2** LLM 设计用例思考不全面 → 需要人工辅助介入
- **问题3** LLM 不能正确理解全部业务场景 → 需要拆解成图/表结构

三个问题在 2026-09-16 构件提炼里已被诊断：

| 问题 | ←→ 构件 |
|:--|:--|
| 问题1 | C3 / C3b / N1 —— 方向类必须逐条实证，不可复用 |
| 问题2 | T2 / C4 / C7 —— 能推出的不交给 LLM；期望层不可满足是 LLM 补不出的缺口 |
| 问题3 | C1 / D8 / D9 —— 条件列最易丢；语义矛盾层检查几乎空白 |

新架构**不是另起炉灶**，而是把 **C3b + T2 + C7 三条构件从「事后排查套路」升级为「事前流程节点」**。

## 一、总原则（跨 Phase 不变的四条）

**原则1 落点登记（C7）**：每个条件/步骤/断言都要能指出——落点（哪个字段/哪步/哪个断言）+ 后果面（改变了哪些构造面）。
> 本次教训：「有字段、无后果」是条件列丢失的唯一防线

**原则2 实证状态字段（C5）**：凡未经实跑或探针验证的映射，一律带
`evidence_status = documented | probed | unknown`
未实证的项**不进生成侧**

**原则3 确定性优先（T2）**：能由权威表/探测结果推出来的，一律不交给 LLM
LLM 只负责「怎么改」，不负责「有没有错」

**原则4 检查要可判错（D3/D5）**：每条新检查配一条「换回旧实现就该红」的验证，否则会积累**恒真检查**

## 二、Phase A —— 摄取 + 接口探测（增）

### A.0 原有工作（不变）
产品文档 / Axure / 接口文档 摄取 → SQLite + ChromaDB

### A.1 新增：接口导入后探测
目标：判定接口文档准确性，给每个 api_def 挂实证状态

#### A.1.1 探测输出：证据状态字段
每个 api_def 的字段/行为挂：
- `evidence_status = documented | probed | unknown`
- `evidence_source = 文档行号 / 探测脚本名 / 探针时间`
- `conflict = 文档与探测不一致时的登记项`

#### A.1.2 探测分层（按成本从低到高）
1. **第一层 只读/查询接口探测** —— 无副作用，先跑
2. **第二层 写接口探测** —— 需要隔离数据 + 清理（参考 G10 探针目录约定）
3. **第三层 边界/异常探测** —— 参数越界、并发、时序

#### A.1.3 探测结果的使用（关键）
探测结果**【不替换】文档**，只补 `evidence_status`

文档与探测冲突 → 走 C8 权威优先级：
- xlsx/文档是权威 → 登记请用户裁决，不自行改
- 探测是事实 → 若文档明确写错，登记 E 编号挂起

探测脚本必须可复跑、幂等：
- 先备份 → **可复跑 0 变更** 才可信（G10 约定）

#### A.1.4 探测与文档比对 = 一次「部署一致性检查」的变体
复用 D4 思路：
按当前源码/实际行为当场取一份 → 与文档逐字段比对 → 要求「不同 0」
**差异清单 = 待裁决项，不是自动改文档**

### A.2 Phase A 检查点

| 编号 | 检查 | 级别 |
|:--|:--|:--|
| 检查A-1 | 每个 api_def 是否有 `evidence_status` 字段 | P0 |
| 检查A-2 | 冲突项是否全部登记 + 挂起，无静默通过 | P0 |
| 检查A-3 | 探测脚本可复跑，二次运行 0 变更 | P1 |
| 检查A-4 | 只读接口探测覆盖率 ≥ 阈值（分母硬锁，D5） | P1 |

## 三、Phase B —— 用例导入 + 语义匹配（重构）

### B.0 定位变化
- **旧**：用户输入需求 → LLM 全自动生成用例
- **新**：用户导入/人工编写用例（自然语言） → 语义检索匹配接口 → 预填关键数据

**核心转变**：把「LLM 设计用例」降级为「LLM 辅助匹配」，把「用例设计」交回给人（对问题2 的正解）

### B.1 用例导入（人工编写）

#### B.1.1 用例形态：纯自然语言，不涉及接口信息展示
- 主界面：业务语言描述（车牌、时长、期望结果）
- 二级信息（可展开）：
  - 匹配依据 / 置信度 / 命中的接口字段
  - 落点登记（C7）与本用例的对应关系

**【关键设计选择】**
「不展示接口信息」对业务人员友好，但**匹配错误会变成隐形缺陷**。
因此**必须保留可展开的二级信息**，否则 C7 的「有字段、无后果」会以新形式复现：人写了条件，后台匹配丢了后果面，没人发现。

#### B.1.2 语义检索匹配接口：分三段（C2 三点定位）
一个业务用例通常需要**三类接口，不是一个**：
1. **前置接口** —— 造数据（建车场/车辆/规则）
2. **触发接口** —— 执行动作
3. **断言接口** —— 回读验证

每段独立检索、独立审核、独立可替换。避免「一次检索定生死」导致匹配错误不可定位。

#### B.1.3 预填关键数据要分层
- **业务字段**（车牌、时长、期望值）—— 业务口径，人工可改
- **接口字段**（URL、method、header）—— 生成侧，只在二级展开

两层不要混在一个预填动作里，否则回到 C5 的反例（「支持一人多车」映射带草案状态就进生成侧，方向恰好相反）

#### B.1.4 落点 + 后果面登记（C7）
每个非空的用例格 → 必须能指出：
- **落点** = 车场字段 / 前置步骤 / 用例步骤 / 断言
- **后果面** = 这个条件改变了哪些构造面

「有字段、无后果」= **直接报错**，不进入生成侧。

### B.2 Phase B 检查点

| 编号 | 检查 | 级别 |
|:--|:--|:--|
| 检查B-1 | 每用例的条件/步骤/断言都有落点登记 | P0 |
| 检查B-2 | 每个条件有后果面登记（≥1 个构造面） | P0 |
| 检查B-3 | 三段接口匹配各自有置信度，低置信度标人工审核 | P1 |
| 检查B-4 | 预填数据业务字段/接口字段分离 | P1 |
| 检查B-5 | 映射项带 `evidence_status`，`unknown` 不进生成侧（复用 C5） | P0 |

## 四、Phase C —— 生成 + 执行 + 多轮调整（增）

### C.0 原有工作（保留）
`.py` 生成 / YAML 生成 / 后校验 / 修复循环

### C.1 提示词按构件整体调整
- 去掉「让 LLM 判对错」的部分，只留「怎么改」（T2）
- 把落点登记/后果面/`evidence_status` 作为**显式输入**喂给 prompt
- 校验规则从「结构层」向「条件语义层」延伸（D8/D9）
- 修复轮放行 thinking（已有：`json_mode` 强制 `thinking=off` 会被 8192 截断）

### C.2 新增：用例执行（MCP 注册测试框架执行命令）
把 pytest / 测试框架执行命令注册为 MCP 工具
生成侧产出 → MCP 调用执行 → 回传结果 → 进判障

### C.3 执行轮次结束后的三层判障（D6）
**必须先定义收敛标准**，否则「多轮对话直至可用」会把产品 Bug 当「用例不可用」反复改数据（D7 失效点的翻版）

| 执行结果 | 归属 | 动作 |
|:--|:--|:--|
| 通过 | 用例可用 | 归档 |
| 用例缺陷 | 数据/步骤/断言错 | 进多轮对话调整 |
| 产品缺陷 | 接口行为与规格不符 | 登记 Bug，用例保持 |
| 环境问题 | 连通性/清理 | 定向重跑（D7） |

**关键：产品缺陷【不算用例失败】，用例保持不动，只登记 Bug。**

### C.4 多轮对话 + 用户调整用例
- **触发条件**：仅「用例缺陷」这一类进入多轮对话
- **对话内容**：
  - 展示失败证据（哪一步、哪个断言）
  - 展示落点/后果面（帮助用户判断是数据错还是期望错）
- **用户调整** → 回 Phase B 的**用例层**（不直接改生成侧）
- **收敛判据**：
  - 达到「通过」或「判定为产品缺陷」即收敛
  - **不设「无限轮直到绿」**，设轮次上限 + 人工接管

### C.5 执行轮里的确定性（T2 延伸）
「怎么判失败」应该是**确定性**的，不是 LLM 判：
- 断言比对 → **代码判定**
- 三层归类 → **规则/相容表判定**（D8）
- LLM 只负责「**怎么改**用例」

### C.6 Phase C 检查点

| 编号 | 检查 | 级别 |
|:--|:--|:--|
| 检查C-1 | 每条新检查配反向锁（换回旧实现就该红）（D3） | P0 |
| 检查C-2 | 硬锁分母（锁定检查到 N 处 + fixture 数硬数字）（D5） | P1 |
| 检查C-3 | 产品缺陷与用例缺陷分离，产品缺陷不改用例 | P0 |
| 检查C-4 | 多轮对话轮次上限 + 人工接管点已定义 | P1 |

## 五、跨 Phase 的公共构件（必须落成代码）

### 构件1 落点 + 后果面登记表
- **位置**：Phase B 用例层 → Phase C 消费
- **形式**：每用例一张表，行=格，列=[落点类型, 落点值, 后果面]
- **检查**：非空格必须有行；后果面为空 → 报错

### 构件2 `evidence_status` 字段
- **位置**：`api_defs` / 映射文件
- **取值**：`documented | probed | unknown`
- **规则**：`unknown` 不进生成侧（C5）

### 构件3 分层判障器（D6）
- **位置**：Phase C 执行轮
- **输入**：执行结果 + 断言比对
- **输出**：`{通过 | 用例缺陷 | 产品缺陷 | 环境问题}`
- **要求**：确定性，LLM 不参与判障

### 构件4 反向锁注册表（D3）
- **位置**：所有新检查旁边
- **形式**：每条检查配一条「旧实现就该红」的测试
- **要求**：逐场景列，如实登记覆盖不到的角落（C9）

### 构件5 一致性检查器（D4 复用）
- **用途1**：Phase A 探测结果 vs 文档比对
- **用途2**：Phase C 产物 vs 源码重生成比对
- **注意**：不能用「部署目录跟自检比」——那是**恒真检查**

## 六、落地顺序建议

| 步 | 内容 | 理由 / 依赖 |
|--:|:--|:--|
| 第一步 | **落点 + 后果面登记表（构件1）** | 最小成本、最高收益，是 C7 的唯一防线 |
| 第二步 | **`evidence_status` 字段（构件2）** | 阻断「未实证进生成侧」 |
| 第三步 | **Phase C 分层判障器（构件3）** | 先定义收敛标准，再上 MCP 执行；否则多轮对话会把产品 Bug 当用例 Bug 改 |
| 第四步 | **Phase A 接口探测（A.1）** | 依赖构件2 的字段先就位 |
| 第五步 | **Phase B 用例导入 + 语义匹配（B.1）** | 依赖构件1 落点登记先就位 |
| 第六步 | **MCP 执行 + 多轮对话（C.2/C.4）** | 依赖构件3 判障先就位 |

**注意：不要先上 MCP 执行再补判障标准，顺序反了会积累返工。**

## 七、明确不做 / 边界

| # | 不做 | 原因 |
|--:|:--|:--|
| 不做1 | 探测结果自动替换文档 | 走 C8 权威优先级，登记请用户裁决 |
| 不做2 | LLM 判「用例是否成立」 | 期望层是否可满足是**相容表**问题（D8），不是 LLM 问题 |
| 不做3 | 「无限轮直到全绿」 | 产品缺陷永远绿不了，必须有「判定为产品缺陷」出口 |

| 不做5 | 在多轮对话里直接改生成侧产物 | 用户调整回用例层，生成侧由确定性内核重出（T2） |
