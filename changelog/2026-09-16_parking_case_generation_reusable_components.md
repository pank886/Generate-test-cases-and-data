## 一、C：分析方法（可复用的「怎么想」）

> 分类轴：**它回答什么问题**。「定位」问问题出在哪一步，「取证」问事实是什么，「设计」问数据怎么造，「判定」问结论能不能成立。

### C-A 定位类 —— 问题出在哪一步

#### C2 三点定位法（上游权威 → 中间映射 → 下游产物）
**做法**：结论出现疑问时，不猜、不倒推，沿「权威输入 → 映射层 → 产物」三点各取一份，逐点比对，把「哪一步丢的」落到具体文件的具体行。
**本次成果**：设计草案 `rule_table_cases_draft.md:61` 有 → 映射草案 `rule_table_interface_map_draft.md:14` 未实证 → 内核 `yaml_kernel.py:595` 无条件套 multi。【实测】
**可复用性**：与业务无关；凡「权威表 → 代码/配置 → 产物」三段式的产品都适用。

### C-B 取证类 —— 事实（方向）到底是什么

#### C3 单变量对照法（定方向）
**做法**：同一份请求体，**只改一个变量**，比对返回。判「列取值『是/否』↔ 接口字段值」的**方向**。
**本次成果**：`carWhiteOtherIsCasual` = true ⇒ 白名单副车按临停(`parkingType 2`)；false ⇒ 副车仍白名单(`4`)；`tempCarIn` 对副车类型**无影响**。包月侧由 `mock/monthlyCar/add` 的 `mainCount` 决定（2=副车算包月、1=副车落临停）。【实测】

#### C3b 跨过漂移的单变量法
**做法**：产物/环境存在**漂移**（被手改、被别的批次污染）时，**不用前后对照**（前后差里混着漂移），改用**同源对照**：同时刻存在的几个配置变体互相比较。
**本次成果**：部署产物里 10 个文件被单独改过（见事实记录 §三），P1/P2/P3 三组同源对照仍然成立，结论不依赖漂移。【实测】

### C-C 设计类 —— 数据/配方怎么造

#### C1 判定表逐列语义归属
**做法**：把 xlsx 每一列判为三类之一——**条件列**（→ 车场配置/前置数据）、**动作列**（→ 用例步骤）、**结论列**（→ 断言）；`\` = 原表「不适用」，**保留展示**以便核对，不折算成 false。
**为什么可复用**：任何「判定表/决策表驱动」的产品都适用，与停车业务无关。
**注意**：三类之中**条件列最容易丢**——它既不在步骤里也不在断言里，没有被比对的对象（见 D9）。【实测】

#### C6 同条件值聚类（条件驱动 vs 用例驱动）
**做法**：把**条件列取值相同**的行聚为一组，要求组内产物形态一致；配方按**条件值**分叉，不按**用例号**分叉。
**本次反例**：同为 c4=否，包月侧副车写法在 表1-20（`mainCount:1`）与 表1-21（`mainCount:2`）上是两个值。【实测】

#### C7 落点登记 + 后果面登记
**做法**：每个非 `\` 的格都要能指出**落点**（车场字段 / 前置步骤 / 用例步骤 / 断言）；**且**要登记它的**后果面**——这个条件改变了哪些**构造面**。
**本次成果**：c4 改了**两个面**（车场开关 + 车辆记录副车写法），只有第一个有承接 ⇒「**有字段、无后果**」。这是本次最核心的一条教训。【实测】

### C-D 判定类 —— 结论成不成立、映射能不能用

#### C4 组内自足判断（判「依赖」的正问法）
**做法**：问「**本用例的期望，它所需的状态能不能由本用例自己的前置造出来**」。
**反例（错误问法）**：「有没有跨用例引用键」——本次扫描报 12 例「跨用例引用 `unpaidFee`」，实际每个用例的步骤里都自己定义了该键，是**假阳性**。
**本次成果**：表1-10 的期望（B 不准入）实际需要「B 转临停」这个中间状态，而它由 表1-09 描述、从未搬进 表1-10 的前置。【实测】

#### C5 未实证不猜（待定栏）
**做法**：映射/口径里凡未经实跑或探针验证的，一律标「待定」并写明「怎么才能定」，**不写进生成侧**（MANIFEST H9 的两栏就是这个做法）。
**本次反例**：「支持一人多车」这一列的映射带着「草案 v1 / §七 待你确认」的状态就进了映射层，方向恰好相反。【实测】

#### C8 权威优先级
**做法**：xlsx 是权威；产物与权威冲突时**改产物**（或登记请用户裁决），**不改权威**；我方生成的用例不得编辑用户 xlsx。
**本次实例**：表1-22 的「是」标在白名单列而车型是包月车 → 登记待裁决，不自行改表。【实测】

#### C9 反向验证（绿灯不算数）
**做法**：改动完成后，把**改动前的实现换回去**，确认新测试会**红**；只绿一次不算验证。
**本次实例（09-15）**：三处改动逐一换回旧实现，确认对应测试变红，并**如实登记一处局限**（某测试在场景 A 下不会红，因为它守的是另一个 Bug）。【盘点】

## 二、D：检测方法（可复用的「怎么判错」）

> 分类轴：**检查发生在哪一层**。越靠前的层越便宜（秒级、不依赖环境），越靠后的层越贵但越接近真相。

### D-A 产物静态层（读产物，不跑接口）

#### D1 静态产物锁
**做法**：断言整个仓库**产出的 YAML 文本**，逐例读、逐键比对。跑得快、不依赖环境、可进 CI。
**已有实例（`tests/test_rule_table_yaml.py` 约 66 条）**：引用闭包（setup/case/teardown 引用的键都有定义）、唯一化（无字面量 parkName）、`bindPayCode` 必走回读、mock 面不断 `retCode` 包络、有效期窗口覆盖时间线基准、临停车牌逐例隔离、共享键单写、提取键无双写者、时刻早于用户截止日、`parkingType` 与车辆类型一致……【盘点】

#### D5 硬锁分母（数量锁 + 覆盖锁）
**做法**：把「检查到 N 处」写成断言，不做静默通过；把集合大小写成硬数字。
**已有实例**：「锁定检查到 8 处」；「fixture 数 == 48」（当时数出来 47，才发现了「只被依赖、没有用例直接引用的编号没落成 fixture」这个真缺陷）。【盘点】

### D-B 生成期闸门（生成过程中拦）

#### D2 分级回炉闸门
**做法**：检查项带 **severity**；P0/P1 → 进修复轮（有独立预算，可追加轮次）；P2 → 只告警 + 写 `_post_validation_issues.json`。
**已有实例**：`YamlPostValidator`（delete body 包裹 P0 / 动态断言 key P1 / 断言键白名单 P0 / 引号配对 P2）、V1–V5（`bindPayCode` 五种形态）、D4（`__MISSING_KEY__` 引用 P1，**不进修复轮**——根因是 setup 生成失败，重生成无用）。【盘点】

#### D8 检查的分层归属
**做法**：**结构 / 格式 / 引用存在性** → 机械判定（可代码化）；**语义矛盾**（断言与前置是否自洽）→ 需要一张**相容表**（身份 ↔ 期望值）才能机械化。
**本次成果**：现有检查在结构层很厚、在**条件语义层几乎空白**。【实测】

### D-C 部署一致性层（产物 vs 源码）

#### D4 部署一致性检查（把「手改产物」暴露出来）
**做法**：**按当前源码当场重生成**到临时目录，与部署目录逐文件比对（比对前抹掉日期戳等易变项）；要求「不同 0」。
**本次成果**：`相同 78 | 不同 10 | 仅部署侧有 1`；10 个不同文件与 mtime 名单**逐一对应** ⇒ 手改产物无处藏身。【实测】
**注意**：该工具的「部署后自检」是**同一性比对**（拿部署目录跟自己比），恒真、证明不了任何事；真正有效的是 `--check`（临时目录重生成比对）；另外部署时**不清残留**（陈旧的单文件 `setup_parking_rule_table.yaml` 仍在）。【盘点：E12】

### D-D 运行期层（实跑之后）

#### D6 三层判障 + 逐例 Bug 归属
**做法**：跑两轮；失败按**连通性 / 契约 / 业务逻辑**三层排查；逐例归因为**测试数据 / 接口缺陷 / 环境**，并写明证据。
**价值**：把「一批红」拆成可处置的三类，避免在接口缺陷上反复改用例数据。【盘点】

#### D7 失败数据双落点 + 定向重跑
**做法**：失败数据同时写原位日志与**每 YAML 旁的 sidecar**（只留最新一轮）；重跑只跑「实际失败用例 + 导致失败的上游 setup」。
**注意（已知失效点）**：「class → setup 文件」映射只认**类级** `usefixtures`，前置拆到方法级后失效 ⇒ 前置失败不再归到 setup 文件、定向重跑不再带前置。【盘点：E11】

### D-E 检查自身的可信度

#### D3 反向锁（改进前的实现必须让它红）
**做法**：每条新检查配一条「把旧实现换回去就该红」的验证，否则这条检查没有判别力。
**注意**：反向锁要**逐场景**列，并如实登记覆盖不到的角落（见 C9）。【盘点】

### D-F 盲区（待补的检查）

#### D9 五条检查盲区（本次定位，均可机械化）
| 盲区 | 现有状态 | 可机械化判据 |
|:--|:--|:--|
| 条件列在产物里有无落点 | 无检查（`rule_tables` 侧只有断言列的部分锁） | 每行每列（非 `\`）→ 落点登记 → 在产物里查找 |
| 断言与自身前置是否自洽 | 无检查（`test_parking_type_matches_vehicle_kind` **只锁三例**；`test_ab_denied_second_car` **只锁结论不锁成因**） | 相容表：断言 `parkingType N` ⟺ 该车前置身份 |
| 映射是否已实证 | 无检查（映射是「草案 v1」原样继承） | 映射项带**实证状态**字段，未实证不进生成侧 |
| 同条件值形态是否一致 | 无检查（配方向按用例号分叉） | 按（车场组 + 各条件列取值）分组，比构造面指纹 |
| 断言列是否每格有落点 | `yaml_kernel.py:864` docstring 声称「由单测 `_assert_coverage` 兜底」——**该测试全仓不存在** | 逐格遍历 + 落点 |

## 三、T：thinking 过程（两层含义，都已成型）

> 分类轴：**谁在想**。「生成器」是 LLM 在推理；「架构侧」是用确定性把推理**换掉**；「排查套路」是人 / Agent 在推理。

### T-A 生成器（LLM 侧）

#### T1 生成器的两段式 thinking（技术构件）
**做法**：同一次生成里先把 LLM 调两次——
① **Phase 1**：`thinking` 打开，产出**自由文本**的分析（测试点分析）；
② **Phase 2**：`json_object` 开关打开、`thinking` 关闭，产出**结构化结果**；Phase 1 的分析回写 state。
**为什么这样切**：结构化输出的约束（json_mode）会**关掉 thinking**，于是「想」和「吐结构」必须分成两段，否则思考空间被挤掉。
**边界事实**：8192 输出上限**跟 `thinking=off` 走**、不跟 `json_object` 走；`thinking=on` 实测可达约 49k token。
**已修的坑**：修复轮曾因 `json_mode` 强制 thinking=off 被 8192 顶截断 → 改为修复轮**放行 thinking**。【盘点：`nodes.py:91-236`、`:49-54`、changelog 2026-09-02 / 2026-09-09】

### T-B 架构侧（用确定性替代 thinking）

#### T2 确定性替代 thinking
**做法**：凡是**能由权威表推出来的**，一律**不交给 LLM**——写成确定性内核（零 LLM），LLM 只负责「怎么改」，不负责「有没有错」。
**本次成果**：`yaml_kernel.py` 全程零 LLM（命名全命中缓存 ⇒ 不调结构化接口；测试里把 `_invoke_structured`/`_invoke_think` 打桩成抛异常，一触即失败）。【盘点】

### T-C 排查套路（人 / Agent 侧）

#### T3 排查的 thinking 套路（按用途再分三类）
| # | 类 | 套路 | 本次实例 |
|--:|:--|:--|:--|
| 1 | 事实观 | **用例即唯一事实** —— 不靠日志/探针推演，直接读产物 | 表1-10 两步、断言取值全部从产物读出 |
| 3 | 事实观 | **区分漂移与真相** —— 产物被手改时，手改不是事实 | P1/P2/P3 同源对照绕过 10 个手改文件 |
| 5 | 事实观 | **区分「断言绿」与「用例成立」** | `test_ab_denied_second_car` 源码版即绿，但期望层不可满足 |
| 4 | 沟通 | **直接回答被问的那个问题**，不扩到相邻议题 | 被问「只有两步」就只答两步的成因 |

| 7 | 纪律 | **方案外发现只登记，不顺手改** | E1–E14、D1（10 个手改文件）全部挂起 |

## 四、G：生成侧可复用构件（代码/数据级）

> 分类轴：**在链路哪一环 + 什么性质**。数据层是声明式事实，代码层是可执行的生成链，知识层是接口事实与铁律，产物形态层决定生成物长什么样，运维约定层决定怎么跑、怎么记。

### G-A 数据层（声明式事实）

| # | 构件 | 位置 | 为什么可复用 | 复用时注意 |
|--:|:--|:--|:--|:--|
| G1 | **映射数据文件（唯一事实源）** | `rule_tables/parking_rule_map.yaml` | 列→字段、分组、配方、动作 token、断言列 全在一处；与代码分离，改口径不用改代码 | 头部声明「xlsx 是权威，本文件只编码推导不出来的东西」——要守住这条边界 |

### G-B 代码层（可执行的生成链）

| # | 构件 | 位置 | 为什么可复用 | 复用时注意 |
|--:|:--|:--|:--|:--|
